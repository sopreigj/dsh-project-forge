# 状态边界：默认按开源写法维护项目

> 本文件是**维护者文档**：说明 `private/` 这个边界存在的理由、边界两侧各放什么、守卫能判什么、
> 以及把项目开源出去的正确动作。协议正文里的 §0 与 §1.7 是它的精简版。

## 一条不变式

> **边界之外（公开面）不得依赖、不得引用边界之内的任何内容，且本身不含私密信息——
> 唯一例外是配置文件：私密值只进配置文件，且必须配一份示例给后来者。**

为什么值得立这条规矩：开源化的两条路线里，"重写历史"（`git-filter-repo` + 轮换凭据 + 协调所有克隆者）
复杂且容易漏；"干净房间重建"（另起仓库、以清理后的代码作为初始提交）简单，代价是丢弃历史。
**如果公开面从第一次 `git init` 起就是干净的，第二条路线的成本趋近于零**——于是开源动作退化成
"删掉边界目录 → 复制 → `git init`"，一个不会出错的动作。

## 边界两侧各放什么

| 位置 | 放什么 | 是否随开源流出 |
|---|---|---|
| `private/` | 四份合同（`steward.md`/`plan.md`/`done.md`/`todo.md`）、两份只追加记录（`journal.jsonl`/`tortuous.jsonl`）、并发认领 `private/.forge-claims/`、本机私密笔记、仅在本地有意义的凭据 | 否（整体删除） |
| 公开面其余部分 | 源码、测试、`README.md`、`LICENSE`、`docs/`、部署描述、示例配置 | 是 |

`private/.forge-claims/` 是本模式运行期的临时文件，必须进 `.gitignore`，永不提交。

## 配置文件例外：抽象 + 示例孪生

边界外唯一允许携带私密值的地方是**配置文件**，且必须成对出现：

```
config.toml            # 真实值；gitignore 掉，或放进 private/
config.example.toml    # 给陌生人看的样板：字段齐全、值全是占位符
```

代码、注释、提交信息、测试、夹具、文档里**一个私密事实都不能有**：没有个人或内部名字，没有"因为某某原因"
这种只有内部人才懂的理由。任何随机器而变的值（路径、主机、凭据、账号 id）都要走配置。

这条规矩的判据很直白：**把仓库交给一个从没见过你的人，他能配起来并跑起来吗。**

## 开源导出流程

```powershell
# 1. 确认公开面干净（守卫平时的检查 + 一次人工通读）
#    项目根应当只剩：README / LICENSE / .gitignore / 源码 / 测试 / docs / 部署描述
# 2. 复制到新目录，整体排除边界目录与 .git
robocopy <项目根> <新目录> /MIR /XD .git private
# 3. 新仓库从零开始
cd <新目录>; git init; git add -A; git commit -m "chore: initial public commit"
# 4. 推送需要用户在本会话内明确授权（协议 §1.2 的一次性授权行）
```

第 2 步用"复制并排除"而不是"删除后再复制"，是为了让原项目保持可回滚：`private/` 不动，
新目录里根本没有它。

## 隐私守卫判什么、不判什么

`guardPrivacyBoundary` 在 `git commit` 时扫描**即将发布的公开面文件**（索引里的 + 工作区改动的），
只判三件不需要判断力的事：

1. **本机家目录路径**：`C:\Users\…`、`/home/…`、`/Users/…`、`/root/` —— 公开文件永远不需要这个事实。
2. **源码伸进边界**：源码/脚本文件里出现 `private/…` 这种具体路径。导出后该路径不存在，等于埋了个死引用。
   （markdown 等散文可以**描述**边界这条规矩，所以只查源码类扩展名。）
3. **配置文件之外的高置信密钥字面量**：`api_key = "…"`（≥16 位）、`-----BEGIN … PRIVATE KEY-----`。

它**不判**：这段文字读起来是否公开、注释里有没有内部八卦、变量名是否泄露产品计划。这些是判断，
不是判定；协议 §1.7 的纪律才是真正的防线。

自我豁免：文件里出现 `privacy-guard: allow` 即跳过扫描。模式自己的实现与夹具带着它（因为它们必须展示反例），
这是**记录在案的偏差**（见 `private/steward.md`），不是给偷懒留的后门。

另一个相关守卫是 `guardSecrets`：边界外出现 `.env`/`*.pem`/`credentials.*` 一律拒绝提交；边界内允许
（本地仓库自留凭据是合理的，它永远不会离开这台机器）。

## 兼容与迁移

- **旧项目照常工作**：digest 先找 `<stateDir>/<名字>`，找不到再找项目根的同名文件；自带规则先找
  `private/steward.md`，再找 `.agents/steward.md`、`steward.md`。所以文档仍在根目录、规则仍在
  `.agents/` 的老项目不会被这次改动打断，只是还没有边界。
- **迁移一个老项目**：把根目录的合同与记录（`done.md`、`plan.md`、`todo.md`，以及只追加的记录文件）
  `git mv` 进 `private/`，规则从 `.agents/steward.md` 移到 `private/steward.md`，`.gitignore` 里把认领目录
  改成 `private/.forge-claims/`，并在同一次提交里更新 `done.md`（§7.7 要求记录搬迁）。
- **不想要边界**：把配置 `stateDir` 设为 `'.'`，文档就回到项目根，行为与引入边界之前一致。
- **测试项目**：顶层 `test/` 项目自带它自己的 `test/private/`（§7.3），边界是逐项目根的，不跨层共享。

## 词汇

| 概念 | 用词 |
|---|---|
| 这个目录 | 状态边界（state boundary），配置键 `stateDir`，默认 `private/` |
| 边界之外 | 公开面（public surface） |
| 边界里那四份要遵守/参照的文档 | 合同（contract，`steward.md`/`plan.md`/`done.md`/`todo.md`） |
| 仓库自带规则 | `private/steward.md`（steward rules） |
| 配置文件的样板 | 示例配置（example twin，`*.example.*`） |
